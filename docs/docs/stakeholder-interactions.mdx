## 2. Requirements discussed with the client

Pulled directly from meeting transcripts, mapped against the course's Key Requirements of All Projects and the tutor-management feature brief — demonstrating requirements were actually walked through with the client, not assumed.

### 2.1 Architecture & non-monolithic split

- Client mandated client-server architecture with strict frontend/backend separation, explicitly warning against frameworks that bundle both layers (10 Aug, 00:04:28).
- Recommended stack: React frontend, ExpressJS backend — confirmed and reaffirmed in the 17 Aug follow-up (00:00:03).

### 2.2 API design

- Client required hand-written REST APIs, explicitly prohibiting auto-generated CRUD from tools like Firebase/Supabase (10 Aug, 00:08:30).
- Controller-based architecture mandated — a dedicated folder for request-handling logic, to keep application logic explicit and owned by the team.

### 2.3 Authentication

- Client confirmed Firebase (or Supabase) as the authentication approach, supporting email/password and Google sign-in (10 Aug, 00:15:37).
- Explicit requirement that authentication rely on an established library rather than a custom-built system — consistent with the course's Key Requirements.

### 2.4 Deployment

- Split hosting strategy agreed: Vercel for frontend, Azure for backend/database, to isolate issues between layers (10 Aug, 00:12:35).
- Interim requirement: deploy a placeholder page to both hosts by end of week, to demonstrate environment setup before feature work begins.
- 17 Aug follow-up confirmed a service is live on Azure; CD workflow flagged as still incomplete and tracked as an open item (00:06:48).

### 2.5 Version control & review process

- Feature-branch workflow mandated: every change developed on its own branch (10 Aug, 00:07:14).
- Two-approval requirement for all pull requests before merge, specifically to ensure equal participation across all 6 members (10 Aug, 00:07:14–00:12:35).
- 17 Aug meeting escalated this into a concrete review method: pulling branches locally and testing before approval, rather than reviewing on GitHub/Gitea alone (00:44:36).
- Agreed policy: stale or problematic pull requests requiring major fixes are closed and reopened fresh, rather than left inactive — discussed directly in response to a real pull request during the 17 Aug meeting (00:41:00–00:48:22).

### 2.6 Testing standards

- Client raised test-driven development directly and questioned whether trivial tests were being used to satisfy requirements (17 Aug, 00:42:31).
- Team and client agreed: trivial/placeholder tests are insufficient — pull requests must include substantive tests tied to real functionality (e.g. email validation) before merge (17 Aug, 00:43:35).

### 2.7 Accessibility & responsiveness

- Client explicitly required mobile responsiveness and accessibility — the application must adapt gracefully across screen sizes without removing functionality (17 Aug, 00:18:28, 00:21:35).

### 2.8 Grading structure & Sprint 1 expectations

- Client clarified milestones account for 70% of the total project grade, and that tutors (not the lecturer) mark sprints and milestones (17 Aug, 00:02:59, 00:24:30).
- Client confirmed the Sprint 1 deadline (25 Aug) and committed to providing a specific demonstration checklist by the following Wednesday (17 Aug, 00:09:59).
- Client set a concrete Sprint 1 demo requirement: a functional login/sign-up flow must be shown live at the sprint meeting (17 Aug, 00:08:06).

### 2.9 External API integration & documentation

- Potential external API integration discussed as a requirement to fulfil (17 Aug, 00:19:55) — specific service still to be finalised by the team.
- Client confirmed documentation is correctly deployed via GitHub Pages, satisfying the course's public documentation site requirement.

### 2.10 Technical implementation decisions

- Team proposed and the group aligned on an async error-handling wrapper to replace repetitive try-catch blocks across asynchronous functions, discussed and debated for trade-offs before adoption, in line with the team's agile/iterative approach (17 Aug, 00:49:26–00:53:03).

## 8. Requirements discussed with the client (Sprint 2)

As with Sprint 1, pulled directly from the meeting records, in the order discussed.

### 8.1 Availability & timetable entry

- Applicants enter their weekly availability manually through the calendar for now — enough to stop a tutor being recommended for a course that clashes with their lectures; PDF timetable import is planned future work (10 Sep, 00:00:00–00:01:04).
- Client questioned the reliability of unverified manual availability (e.g. exam clashes); the team explained the system produces suggestions and organisers retain final override authority — accepted, with timetable import acknowledged as an advanced future feature (13 Sep, 00:28:39–00:33:54).
- The four role views were confirmed as admin, tutor, student, and lecturer (10 Sep, 00:19:12); the organiser assignment interface was additionally demonstrated live on 13 Sep (00:38:05).

### 8.2 Notifications & session attendance

- Email notification to a tutor when they are assigned to a course is live (10 Sep, 00:02:37) and was demonstrated with the organiser assignment interface, including an "auto" action that selects the top candidates by marks (13 Sep, 00:38:05–00:40:47).
- A QR-code digital register for session sign-in/sign-out — mirroring the university's tutorial attendance system — is planned as a future phase (10 Sep, 00:02:37); the client later suggested a secret verification code for event attendance to replace manual supervisor sign-offs (13 Sep, 01:49:39).
- During the assignment demo, the client flagged the risk of accidental clicks sending assignment-removal emails; the team agreed to add a confirmation prompt before saving assignment changes (13 Sep, 00:39:42).

### 8.3 Testing standards & API testing

- 90% unit test coverage is now required on every pull request before it can be merged, enforced at review time (10 Sep, 00:05:03).
- API testing is required for Milestone 2: every endpoint must be verified to return the expected status codes and response structures, with parameters as defined — the client recommended Postman and Newman (10 Sep, 00:06:23–00:09:55).
- The testing procedure itself must be documented on the documentation site, with screenshots of Postman requests as evidence (13 Sep, 00:52:53–00:57:54).

### 8.4 API deployment

- The API must be deployed so third parties can use it — with permissions, and documentation of what each endpoint expects and returns — the client suggested Render or Railway; the team added the requirement to its issue tracker (10 Sep, 00:09:55–00:11:32).
- Where API documentation is presented as an interactive endpoint listing (Swagger-style), the client expressed a preference for that format (13 Sep, 00:52:53).

### 8.5 User feedback evidence

- Feedback collection requires evidence — a form (e.g. Google Forms) plus analytics showing how many people responded, with a target of roughly 10 responses, and documentation showing the feedback was collected and then acted on (10 Sep, 00:11:32–00:16:17).
- The client confirmed the feedback does not need to come from live external users at this stage — the team may submit the entries itself, provided the evidence trail (the form and its response data) is preserved and shows follow-through (10 Sep, 00:14:55).
- Reaffirmed on 13 Sep: a Google Form is to be created, its responses summarised on the documentation site, and used to justify improvements (00:57:54–01:00:36).

### 8.6 Third-party code documentation

- Any third-party code used (e.g. Firebase) must be documented with a clear motivation for why external code was chosen over writing our own (10 Sep, 00:16:17).

### 8.7 Volunteering & overflow work

- The client identified the volunteering feature as missing: an organiser posts a session shortage, students volunteer, and the organiser approves the requests (10 Sep, 00:19:12–00:24:49).
- Scope aligned on 13 Sep: overflow work covers administrative tasks, marking, and invigilation when tutor staffing is insufficient, and volunteers are existing tutors stepping in during overflow — not a separate user group (02:13:01–02:31:40).
- The client questioned why users must apply to volunteer before viewing opportunities; the team defended filtering candidates by scheduling criteria to avoid emailing roughly 300 students when only a few positions are needed — the client accepted the design provided the team can defend it under scrutiny (13 Sep, 00:15:29–00:25:54).
- The excuses feature will track how many tutors have excused themselves from a session, so a shift can be opened for volunteering once a threshold is exceeded (13 Sep, 02:35:18).

### 8.8 Timesheets, approvals & signatures

- The timesheet feature is required, including requesting signatures from authorisers, with a notification to the person responsible for signing (10 Sep, 00:20:36).
- The full workflow was demonstrated live (13 Sep, 01:50:47–01:55:31): a lecturer creates a course event, the allocated tutor claims it into a timesheet, entries and titles update in real time, submission locks the timesheet against edits, and a supervising lecturer approves or rejects it — rejection by any single supervisor rejects the whole timesheet.
- The signature requirement was debated (13 Sep, 01:56:41–02:02:23): although the web app tracks approvals digitally, payroll operates outside the system and still needs a supervisor's physical signature on the PDF timesheet — the team concluded signature requirements must align with payroll's operational needs. Approved timesheets export as a correctly populated PDF for exactly this purpose (demonstrated 01:59:03).

### 8.9 Course applications & governance

- The client ruled that lecturers must not independently open applications and dictate tutor numbers without organiser review; the team committed to adding a pending-review status and the ability to manually close a course's application process (13 Sep, 01:31:45–01:33:16).
- Lecturers specify the maximum weekly hours required for their courses (13 Sep, 00:48:55).
- Course applications are filtered by the applicant's availability — opportunities only appear when the timetable matches — and an applicant's slot selection locks while the application is pending, preventing scheduling inconsistencies (13 Sep, 01:34:38–01:37:12).
- The claimable-hours cap is enforced at application time: a second course that would push an applicant over the weekly limit is blocked with an explanatory warning — the client reviewed and confirmed the validation logic (13 Sep, 01:43:26–01:44:54).

### 8.10 System configuration & payroll

- Organiser-managed, system-wide settings drive the claim rules: the maximum claimable hours and the event claim window (demonstrated with test values of 3 hours and one month), and hourly pay rates by year of study feed the automatic payout calculation on timesheets (13 Sep, 01:08:50–01:14:36).
- An uploaded PDF payroll template is used to generate the finalised timesheet exports (13 Sep, 01:15:32).
- The client critiqued the "Settings" label for organisation-wide standards (it suggests personal profile management); a rename was agreed for later (13 Sep, 01:11:21–01:12:32).
- The client suggested an onboarding tutorial guide for first-time users, acknowledged as a valid future addition (13 Sep, 00:51:05).

### 8.11 Infrastructure & deployment

- The database was migrated to a new Azure server after the previous account's free trial expired (attributed to hosting several projects on one server); the new database is live (10 Sep, 00:03:51).
- The live database was verified working on 13 Sep; local databases must be deleted and the app restarted to reconnect, and dependencies were downgraded for compatibility with the stable Node 22 runtime (13 Sep).
- Frontend deployment to Vercel was in progress: the workflow had a build step but no deploy step, and required the project ID and token secrets (13 Sep, 02:50:33–02:53:47).
- Frontend error handling was called out: login failures were silent because only 200-status responses were handled, while the backend already returns standard 403/404 codes — flagged for fixing (13 Sep, 00:06:57–00:08:09).

### 8.12 Review & merging strategy

- A backlog of 10–11 pull requests with merge conflicts and slow approvals led to a paired-merging agreement: each PR author pairs with a designated reviewer, briefs them directly, and merges — clearing the backlog faster than the general approval queue (13 Sep, 02:05:35–02:07:27).
- Redundant pull requests were closed and working environments re-synchronised with main (13 Sep, 02:16:02–02:18:49).
