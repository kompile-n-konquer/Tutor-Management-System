# TutorFlow REST API

The TutorFlow backend is a **hand-written REST API** built with Node.js and Express. Every endpoint is
defined explicitly in `backend/routes/` — no endpoint is generated by a scaffolding tool — and every
request travels over HTTP(S) as JSON.

## Base URL

| Environment | Base URL |
| --- | --- |
| Production (Azure App Service) | `https://tutor-api.azurewebsites.net/api` |
| Local development | `http://localhost:3000/api` |

All paths below are relative to the base URL, e.g. `GET /users/me` means
`GET https://tutor-api.azurewebsites.net/api/users/me`.

## Authentication

The API uses **Firebase Authentication**. Clients sign in with Firebase (email/password or Google),
receive an ID token, and send it with every request:

```http
Authorization: Bearer <firebase-id-token>
```

Acquiring a token as a web client:

```js
import { getAuth } from 'firebase/auth';

const token = await getAuth().currentUser.getIdToken();
fetch(`${BASE_URL}/users/me`, {
  headers: { Authorization: `Bearer ${token}` },
});
```

The backend verifies every token with the Firebase Admin SDK and loads the caller's database record.
Missing, malformed, or expired tokens return:

```json
{ "error": "Invalid Firebase ID token" }
```

Tokens are short-lived (1 hour) — request a fresh one with `getIdToken()` rather than caching it long-term.

## Roles

Authorization is role-based. The role is stored on the user record and normalised to uppercase:

| Role | Who they are | Typical access |
| --- | --- | --- |
| `STUDENT` | Signed-up students | Own profile, availability, tutoring applications, volunteer views |
| `TUTOR` | Approved tutors | Student access plus assignments, events, timesheets |
| `LECTURER` | Course owners | Own courses/events, timesheet approval for supervised entries |
| `ORGANISER` | Course coordinators | Everything: applications review, allocation, settings, user directory |
| `ADMIN` | System administrators | Same as organiser |

## Conventions

- **Format** — requests and responses are JSON (`Content-Type: application/json`), except file uploads
  (`multipart/form-data`) and PDF downloads.
- **Status codes** — `200` success, `201` created, `204` no content, `400` validation error,
  `401` missing/invalid token, `403` insufficient role/ownership, `404` not found, `409` conflict.
- **Error envelope** — errors raised by controllers share one shape:

  ```json
  {
    "message": "Only a lecturer, organiser or admin can create a course",
    "path": "/api/courses",
    "timestamp": "2026-09-14T10:12:00.000Z"
  }
  ```

- **Timestamps** — ISO 8601 UTC strings.
- **Personal data** — user endpoints never return the `firebaseUid` column; profile lookups are
  restricted to the caller's own record (organisers/admins excepted).

## Users

### `GET /users` — user directory

Organiser/admin view of every registered account. Responses contain only profile fields —
`id`, `studentNumber`, `employeeNumber`, `firstName`, `lastName`, `email`, `phoneNumber`,
`yearOfStudy`, `role`, `isActive`, `createdAt`, `updatedAt`. The Firebase identifier is never exposed.

### `GET /users/me` — own profile

Returns the caller's profile in the same sanitised shape as above.

### `GET /users/verify-role?roles=TUTOR,LECTURER` — role gate check

Returns `{ "role": "TUTOR", "allowed": true }` when the caller's role is in the comma-separated
allow-list, otherwise `403`. The frontend route guards use this to reject direct navigation to
another role's page server-side.

### `GET /users/:firebaseUid` — single profile

Fetches any profile **by the caller's own Firebase UID**. Access is enforced in the controller:
a caller may only look up their own record; organisers and admins may look up anyone.

### `POST /users` — sign up

Creates the caller's own user record after Firebase account creation. The request must carry the
caller's Firebase ID token, and the token's UID (and email, when present) must match the body:

```json
{
  "firstName": "Alan",
  "lastName": "Turing",
  "email": "alan.turing@wits.ac.za",
  "firebaseUid": "the-firebase-uid-of-the-caller"
}
```

Responds `201` with the created profile. A token belonging to a different Firebase account, or an
email mismatch, returns `403`; an already-registered email or UID returns `409`. New users get the
`STUDENT` role.

### `PUT /users` — update own profile

Editable fields only: `firstName`, `lastName`, `phoneNumber`, `yearOfStudy`
(one of `3rd year`, `honours`, `masters`, `phd`). Email and department are read-only.

### `DELETE /users` — deactivate own account

Soft-deletes the caller: sets `isActive: false` in the database and disables the Firebase account.
Responds `204`.

## Courses

### `GET /courses`

All courses with allocation progress (`assignedCount`, `tutorsRequired`, `lecturer` name).

### `POST /courses`

Creates a course with its weekly tutoring slots in one atomic call:

```json
{
  "courseCode": "COMS3007",
  "courseName": "Machine Learning",
  "minimumMark": 70,
  "tutorsRequired": 2,
  "slots": [{ "dayOfWeek": 1, "timeSlotId": 3 }]
}
```

`dayOfWeek` is 0 (Monday) to 4 (Friday); `timeSlotId` references the time-slot catalogue.
Duplicate course codes return `409`.

### `PUT /courses/:courseId` and `PUT /courses/:courseId/slots`

Full course update and slot replacement respectively — both validated the same way as creation.

### `PUT /courses/open-applications`

Opens the application process for the listed courses: `{ "courseIds": [1, 2] }`. Courses that
already have tutors assigned or are already open are skipped, and the response reports
`requestedCount`, `updatedCount` and `skippedCount`.

## Availability

### `GET /availability`

The caller's availability grid plus the time-slot catalogue and slots locked by submitted
applications: `{ timeSlots, availability, lockedSlots }`.

### `PUT /availability`

Replaces the caller's availability wholesale: `{ "availability": [{ "dayOfWeek": 1, "timeSlotId": 3 }] }`.
Locked slots (held by submitted applications) must remain in the set — removing them returns `400`.

## Applications (tutoring opportunities)

Available to students and tutors. Only courses whose tutoring slots fit inside the caller's
availability are returned.

### `GET /applications` / `GET /applications/:courseId`

Opportunity lists/detail with weekly claimable hours and hours-cap warnings (`hoursExceeded`).

### `POST /applications/:courseId/apply`

Body: `{ "courseMark": 82 }`. The server enforces the course's minimum mark, availability coverage,
no duplicate applications (`409`), and the organiser-set claimable-hours cap.

## Onboarding (role applications)

### `POST /onboarding/apply`

Submits an application for the `TUTOR` or `LECTURER` role.

### `GET /onboarding/applications` / `GET /onboarding/applications/:id/rank` / `PATCH /onboarding/applications/:id/review`

Organiser tools: the pending queue, a rank suggestion computed from course marks and availability,
and approve/reject (`{ "action": "approve" }` or `{ "action": "reject", "reason": "..." }`).
Approving a tutor application promotes the user to `TUTOR` and creates their tutor record.

## Allocation

All allocation endpoints are **organiser/admin only** — they expose applicant personal data and
mutate assignments.

### `GET /allocation/available-tutors?courseId=…`

Applicants ranked by course mark (descending), excluding already-assigned applicants.

### `POST /allocation/assignments`

Body: `{ "applicantId": 12, "allocatedHours": 5, "semester": "2026-S2" }`. Creates (or reuses) the
tutor record and the assignment transactionally, then fires a notification email. Enforces the
course's tutor cap (`409` on overflow).

### `DELETE /allocation/assignments/:applicantId` and `.../remove`

Unassign returns the applicant to the pending pool; remove permanently rejects them. Both send an
email notification and respond `204`.

## Events

### `GET /events`

Role-scoped: tutors see events on their allocated courses, lecturers see events on courses they
created, organisers/admins see everything.

### `POST /events` / `PUT /events/:id`

Lecturer-only, own courses only. Body: `{ "courseId": 3, "date": "2026-09-21", "description": "tutoring" }`
where `description` is one of `tutoring`, `marking`, `invigilation`, `admin`. One event per course
per date — duplicates return `409`.

### `GET /events/claimable`

Tutor-only: past, unclaimed events on the tutor's allocated courses, inside the organiser-set
claim window.

## Timesheets

### `GET /timesheets` / `POST /timesheets`

Own timesheets, and creating a draft (optional body `{ "name": "September claim" }`).

### `PUT /timesheets/:id`

Replaces all entries by claiming events — the body only carries event IDs:

```json
{ "name": "September claim", "entries": [{ "eventId": 41 }, { "eventId": 42 }] }
```

Course, date, supervisor and duration are derived server-side from the claimed event; manual
entries are rejected. Every event can be claimed exactly once (`409` on a taken event).

### `POST /timesheets/:id/submit`

Submits for approval; enforces the monthly claimable-hours cap per rolling 31-day window.

### `PUT /timesheets/:id/entries/:entryId/approve` / `PUT /timesheets/:id/reject`

Supervising lecturer (or organiser/admin) actions. Rejection requires a `reason` and resets the
timesheet so the tutor can edit and resubmit. A timesheet becomes `APPROVED` once every entry is
approved.

### `GET /timesheets/:id/export`

Renders an approved timesheet onto the uploaded PDF template and streams it back as
`application/pdf`.

## Sessions & Directed Cover Offers

Future dated sessions follow one coverage lifecycle. A tutor excuses themselves from a session
they no longer attend, which returns it to the open pool; cover then reaches it either through
the volunteer view or through a **directed cover offer** — the excusing tutor nominates one
specific appointed tutor. Either way the course's lecturer gives the final approval and the
session is re-pointed at the covering tutor. No pay changes hands at offer time: the covering
tutor claims the session through their timesheet after it takes place.

Status flow: `SCHEDULED` → (excuse) → `UNASSIGNED` → (nominee accepts, or a volunteer applies) →
`PENDING` → (lecturer approves) → `SCHEDULED`. A declined or withdrawn offer returns the session
to `UNASSIGNED`.

### `GET /sessions/:id/cover-candidates`

Tutor-only, on one of their own excused sessions. Returns every tutor appointed to the session's
course with an `eligible` flag and the blocking constraint `reasons` — availability coverage,
busy blocks, double-booking on the session's date, or the course having no tutoring slot on that
day.

### `POST /sessions/:id/cover-offer`

Body: `{ "nomineeId": 20 }`. Inside one transaction the server re-checks that the session is the
caller's own excused one and has not taken place, that the nominee is appointed to the course and
passes the same constraint checks, and that no other cover request is live for the session.
Constraint failures return `403` with the reasons; a session already offered or covered returns
`409`. Success marks the session `OFFERED`.

### `PATCH /sessions/:id/cover-offer`

Body: `{ "decision": "ACCEPT" }` or `{ "decision": "DECLINE" }`. Only the nominated tutor can
respond while the offer is live. Accepting moves the request to `PENDING` for the lecturer — the
same review an open volunteer request goes through; declining records the refusal and reopens the
session.

### `DELETE /sessions/:id/cover-offer`

Only the tutor who excused the session can withdraw an offer that still awaits the nominee.

### Claiming a covered session

Once approved, only the covering tutor may claim the past event through their timesheet: the
claim endpoint refuses (`409`) any attempt by the tutor who excused themselves to claim a session
another tutor covered through the volunteer flow.

## Settings

### `GET /settings`

Current system settings: `tutorMonthlyClaimableHours`, `tutorEventClaimMonths`, `hourlyRates`
keyed by year of study, and `pdfTemplateFilename`.

### `PUT /settings/…`

Organiser/admin configuration updates (hours cap, claim window, hourly rates, PDF template upload
via `multipart/form-data` field `template`). Values are validated server-side with sensible bounds
(e.g. hourly rates 0–5000 ZAR).

## Service Health

Two unauthenticated endpoints exist purely for infrastructure monitoring and expose no user data:

- `GET /` — `{"message":"TutorFlow API is running","timestamp":"…"}` (Azure health probe)
- `GET /health` — pings the database with `SELECT 1`, returning `healthy` or `503 unhealthy`

## External Service Integrations

The API integrates with two external services over HTTPS:

1. **Firebase Authentication (Google Identity Platform)** — every request's bearer token is
   verified server-side with the Firebase Admin SDK; account deactivation propagates back by
   disabling the Firebase account.
2. **Resend (email delivery)** — transactional notification emails (assignment added/removed,
   timesheet approved/rejected) are sent through the Resend
   HTTP API, with every attempt recorded and de-duplicated in the `EmailLog` table.
